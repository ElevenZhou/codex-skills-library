# Rich HTML Docs

## Core Rule

When the user asks for a standard explanatory Markdown document, create a polished `.html` document instead of `.md` by default. The HTML must be self-contained, visually organized, easy to share, and readable by opening the file directly in a browser.

Use Markdown only when:

- The user explicitly asks for `.md` or Markdown.
- The target repository requires Markdown, such as `README.md`, `CHANGELOG.md`, GitHub issue templates, or docs generated by a Markdown pipeline.
- The content is meant to be pasted into a platform that only accepts Markdown.

If the user says "md" casually while asking for a shareable explanation, prefer HTML and mention briefly that the richer document was created as HTML according to this skill.

## Output Standard

Create a single `.html` file with inline CSS and no external runtime dependencies. Use UTF-8 and include Chinese-friendly typography.

The document should feel like a polished handoff page, not a raw code dump:

- Clear title and short subtitle.
- Status or conclusion block near the top.
- Sectioned layout with cards or bands for key topics.
- Highlight boxes for risks, action items, commands, configuration values, and decisions.
- Tables for mappings, field lists, checks, or comparisons.
- Code blocks for exact snippets.
- A concise "next steps" or "verification" section when useful.

Prefer filenames that match the user intent, for example:

- `飞书多维表格NOTEXIST排错说明.html`
- `聚宽策略部署说明.html`
- `T0策略运行复盘.html`
- `接口配置检查清单.html`

## Writing Guidance

Write for the user's practical workflow. For this user's common coding, strategy, automation, Feishu, and deployment notes:

- Put "what happened / root cause / what to change" at the top.
- Separate "must do now" from "optional improvement".
- Make copy-paste values obvious with code blocks.
- Avoid leaking secrets into generated docs; redact app secrets, tokens, webhooks, cookies, and private keys.
- When documenting fixes for an existing file, include exact file names and line references where available.
- When providing a replacement function or configuration block, keep it complete enough to paste.
- Include a small verification checklist for things the user can confirm in the app, platform, or logs.

## Visual Tone

Prefer clean professional presentation: white panels, restrained accent colors, readable tables, and compact spacing. Avoid decorative clutter, marketing hero layouts, giant gradients, or external fonts. The page should look good when shared as a local file or pasted into an internal knowledge base.

## Delivery

When creating the document, mention the created `.html` file path in the final answer. If a Markdown document already exists from an earlier step and the user now wants this standard applied, create an HTML version next to it and leave the original untouched unless asked to replace it.
